# Автоматизация заявок

В репозитории два приложения:

- `client/`: Nuxt 4 с Tailwind CSS и Nuxt UI (порт 3002).
- `server/`: Express API с Prisma и PostgreSQL (порт 3000).

## Запуск приложения через Docker

Нужны Docker Engine и Docker Compose. Из корня репозитория выполните:

```sh
docker compose up --build --detach --wait
```

Откройте [http://localhost:3002](http://localhost:3002). Compose запускает базу, применяет миграции, создаёт демонстрационных пользователей, загружает исходные данные и запускает сервер и интерфейс. Node.js и pnpm на компьютере не нужны.

Данные из книги включены в `server/equipment-data.json`; Excel для первого запуска не требуется. Ожидается 40 объектов и 1339 записей истории, из них 441 связанная и 898 несопоставленных. Повторный запуск не перезаписывает существующие исходные данные и не удаляет заявки. Если исходные данные загружены лишь частично, автоматическая подготовка остановится с ошибкой.

### Демонстрационные учётные записи


| Роль                 | Логин      | Пароль               |
| -------------------- | ---------- | -------------------- |
| Дежурный             | `duty`     | `demo-duty-2026`     |
| Сервисный инженер    | `engineer` | `demo-engineer-2026` |
| Технический директор | `director` | `demo-director-2026` |


Учётные записи предназначены только для демонстрации.

Если порты заняты, перед запуском задайте `FRONTEND_HOST_PORT`, `HOST_PORT` и `POSTGRES_HOST_PORT`. Например:

```sh
FRONTEND_HOST_PORT=3102 HOST_PORT=3100 POSTGRES_HOST_PORT=55432 docker compose up --build --detach --wait
```

Откройте интерфейс на выбранном `FRONTEND_HOST_PORT`. Для команд запуска используйте одинаковые значения этих переменных.

Чтобы добавить 30 демонстрационных заявок после импорта и создания пользователей, выполните:

```sh
docker compose exec -w /app/server app node scripts/requests-seed.ts
```

При локальном запуске сервера выполните `node scripts/requests-seed.ts` из каталога `server`. Сначала задайте `DATABASE_URL` в окружении или в `server/.env`. Заявки помечены `[Демо]` и содержат журнал действий, сроки и комментарии. Повторный запуск не изменяет существующие демонстрационные заявки и не создаёт дубликаты. Если демонстрационную заявку удалить, следующий запуск создаст её заново. Используйте этот seed только в демонстрационной базе.

Проверьте вход трёх пользователей и API оборудования:

```sh
docker compose exec -w /app/server app node scripts/auth-smoke.ts
docker compose exec -w /app/server app node scripts/equipment-smoke.ts
```

Для ручной проверки входа выполните запросы ниже. В ответе ожидаются HTTP 200, токен и роли DUTY, ENGINEER и DIRECTOR соответственно. Если задан другой `HOST_PORT`, замените порт в адресе:

```sh
curl -i -H 'Content-Type: application/json' -d '{"login":"duty","password":"demo-duty-2026"}' http://localhost:3000/api/auth/login
curl -i -H 'Content-Type: application/json' -d '{"login":"engineer","password":"demo-engineer-2026"}' http://localhost:3000/api/auth/login
curl -i -H 'Content-Type: application/json' -d '{"login":"director","password":"demo-director-2026"}' http://localhost:3000/api/auth/login
```

Ограничения входа описаны в [server/README.md](server/README.md#демонстрационный-вход). Чтобы проверить сохранность данных, перезапустите контейнеры командой `docker compose restart` и повторите обе проверки. Команда `docker compose down` останавливает и удаляет контейнеры, сохраняя том базы. Не используйте `--volumes`, если нужны данные.

## Локальный запуск

Из корня репозитория установите зависимости: `pnpm install --frozen-lockfile`.

- Сервер: скопируйте `server/.env.example` в `server/.env`, настройте `DATABASE_URL`, затем выполните `pnpm dev:server`.
- Клиент: задайте `NUXT_API_BASE` как адрес запущенного сервера и выполните `pnpm dev:client`. Например, для локального сервера: `NUXT_API_BASE=http://127.0.0.1:3000 pnpm dev:client`. Откройте `http://127.0.0.1:3002`.
- Сборка клиента: `pnpm build:client`
- Сборка сервера: `pnpm build:server`
- Общая проверка: `pnpm verify`

Docker Compose запускается из корня командой `docker compose up --build`. Подробности настройки API и БД находятся в [server/README.md](server/README.md).

После импорта данных и создания пользователей войдите как `duty`, `engineer` или `director` с демонстрационными паролями из [инструкции сервера](server/README.md#демонстрационный-вход). Дежурный создаёт заявку и назначает инженера. Назначенный инженер выполняет заявку и завершает её с комментарием. Директор видит сводку, просрочку и нагрузку, может назначить инженера и изменить срок или приоритет. В карточках оборудования доступны исходные атрибуты и история обслуживания.

На сводке директора диаграмма показывает распределение заявок по статусам. Данные берутся из API заявок; при отсутствии заявок отображается сообщение вместо диаграммы.

В списке заявок можно применить поиск и фильтры, затем нажать «Экспорт CSV». Файл содержит только показанные заявки и подходит для передачи сводки; ячейки, похожие на формулы, сохраняются как текст.

Клиент передаёт запросы к API через серверный прокси Nuxt. Токен хранится в HTTP-only cookie, а его хеш и срок действия сессии сохраняются в PostgreSQL. Перезапуск сервера не завершает сессию; повторный вход требуется через 8 часов или после выхода. Демонстрационные учётные записи не предназначены для промышленной эксплуатации.

Если приложение временно не может проверить сессию, появится отдельная страница с кнопкой повторной проверки. После восстановления связи она возвращает на запрошенную страницу без повторного ввода пароля.

## Проверка ручного процесса

Ручные заявки работают без стенда и переменных `IEC104_HOST` и `IEC104_PORT`.

1. Войдите как дежурный, откройте оборудование и найдите генератор `40000001`. В карточке доступны его атрибуты и история. При импорте ожидается отчёт: 40 объектов, 1339 записей, 441 связанная и 898 несопоставленных. Повторный импорт не создаёт дубликатов:

   ```sh
   docker compose exec -w /app/server app node scripts/equipment-import.ts --initial
   ```

2. Создайте заявку на осмотр: выберите оборудование, укажите описание, приоритет и срок. Назначьте инженера при создании или позже в карточке заявки. Директор тоже может назначить инженера и изменить срок или приоритет.
3. Войдите как инженер и откройте назначенную заявку. Нажмите «Взять в работу», затем завершите её с комментарием «Ремонт не потребовался». В карточке проверьте результат и журнал действий.
4. Как дежурный создайте заявку на ремонт и назначьте инженера. Как инженер возьмите её в работу, выберите «Ожидание ЗИП», затем «Вернуть в работу». Попробуйте завершить без комментария: приложение должно отказать. Введите результат, завершите заявку и проверьте журнал.
5. Как директор откройте сводку и проверьте просрочку и число активных назначений инженера. Как дежурный убедитесь, что в обычной заявке нет управления сроком и приоритетом после создания. Сервер также отклоняет такие прямые запросы дежурного; для автоматической заявки ему доступно изменение срока, но не приоритета.
6. Перезапустите приложение командой `docker compose restart`. Снова откройте созданные заявки: статус, результат и журнал должны сохраниться. Не добавляйте `--volumes`: удаление тома приведёт к потере данных.

## Мониторинг ВЭУ

Мониторинг принимает показания по IEC 60870-5-104. Для подключения укажите адрес и порт выданного организаторами стенда в окружении, затем запустите или пересоздайте Compose:

```sh
IEC104_HOST=АДРЕС_СТЕНДА IEC104_PORT=ПОРТ_СТЕНДА docker compose up --build --detach --wait
```

Для локального запуска сервера задайте обе переменные в `server/.env` или окружении. Если параметры не заданы, ручные заявки работают без мониторинга. После запуска откройте `/monitoring`: страница показывает восемь ВЭУ, последние полученные значения и историю. Время относится к приёму сервером; данные считаются свежими только при активном соединении и не более пяти секунд после приёма. Сервер передаёт оставшееся время актуальности, поэтому она не зависит от часов компьютера пользователя. При разрыве связи сохраняются последние значения и показывается общее предупреждение.

Дежурный или директор может прикрепить к ручной заявке неизменяемый снимок последнего полученного статуса ВЭУ. Подтверждённый переход известного неаварийного статуса в `8` создаёт системную заявку на осмотр без срока и без выдуманной связи с объектом реестра. Первый статус после соединения устанавливает исходное состояние, повторное `8` не создаёт дубликат. Дежурный назначает срок и инженера; закрытие, как и для ручных заявок, требует комментария.

Сохранённые статусные наблюдения обрабатываются по порядку. Если создание заявки временно не удалось, приложение повторит обработку и продолжит её после перезапуска. Пакет, который не удалось сохранить в базу, восстановить нельзя; ошибка записи выводится в журнал сервера.

График показывает до 1000 последних наблюдений выбранного сигнала; данные сохраняются в базе. Для мощности, скорости ветра и температуры по умолчанию отображается среднее по группам до 10 последовательных показаний. Краткие пики при усреднении могут быть не видны; для их просмотра включите исходные показания. Статус и направление ветра не усредняются. Если при работе через Docker Desktop подключение к внутреннему адресу стенда недоступно, проверьте маршрутизацию VPN между контейнером и сетью площадки. Доступный порт с компьютера сам по себе не означает, что он доступен из контейнера.

Активная мощность отображается в кВт, реактивная в квар, согласно постановке. Единицы стенда следует подтвердить у организаторов: в формуляре встречаются МВт и Мвар. Клиент отправляет только служебные команды обмена и общего опроса, без команд управления оборудованием.
